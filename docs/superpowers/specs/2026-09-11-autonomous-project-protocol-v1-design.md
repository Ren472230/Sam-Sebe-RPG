# Протокол автономной разработки проекта v1

## Цель

Создать в репозитории устойчивый слой управления разработкой, который позволяет обычному ChatGPT продолжать работу в новом или повторном запуске почти без ручной постановки следующей задачи.

Главный принцип: репозиторий хранит фактическое состояние, цели, очередь развития, ограничения, проверенные результаты и передачу контекста между запусками. История чата считается дополнительным источником и не должна быть обязательна для продолжения работы.

Пилот: `Ren472230/Sam-Sebe-RPG`.

База пилота: PR #53, ветка `integration/audit-results-v1`, исходный HEAD `5f5695f5918ed5dbc4fefea5e6483795a00260d5`.

`main` остаётся без изменений. Слияния в `main` требуют отдельного явного разрешения владельца проекта.

## Зачем это нужно

Сейчас проект уже умеет вести часть автономного цикла через:

- `RUN_STATE.json` – состояние текущей работы;
- `CHAMPION_STATE.json` – последний подтверждённый сильный кандидат;
- `AUTONOMOUS_LEARNING.md` – накопленные выводы автономных циклов;
- `docs/superpowers/specs/` и `docs/superpowers/plans/` – утверждённые решения и планы;
- GitHub Actions – технические проверки.

Проблема состоит в отсутствии единого контракта, который объясняет новому запуску ChatGPT:

1. какие источники считать авторитетными;
2. как восстановить реальное состояние при устаревших документах;
3. как выбрать следующую задачу;
4. как защититься от параллельных запусков;
5. как завершить цикл с понятной передачей следующему запуску;
6. какие действия требуют владельца проекта.

## Область v1

Версия v1 должна дать один воспроизводимый автономный цикл:

`восстановление состояния -> выбор работы -> выполнение -> проверка -> запись результата -> передача следующему запуску`.

Она должна работать через обычный ChatGPT и подключение GitHub. Codex в архитектуру исполнения не входит.

Версия v1 не должна автоматически сливать изменения в `main`, публиковать релизы, менять секреты, включать платные внешние сервисы или выполнять разрушительные миграции.

## Архитектура управляющего слоя

### 1. `AGENTS.md`

Корневой постоянный контракт проекта.

Он должен содержать:

- назначение проекта;
- порядок восстановления состояния;
- порядок приоритетов;
- обязательные ограничения;
- правила веток;
- правила проверки;
- перечень действий с обязательным подтверждением владельца;
- ссылку на подробный автономный регламент.

`AGENTS.md` должен быть коротким и стабильным. Часто меняющееся состояние туда не записывается.

### 2. `docs/autonomy/PROJECT_CHARTER.md`

Хранит долгоживущую цель проекта:

- продуктовую цель;
- текущую границу продукта;
- критерии успеха;
- ключевые архитектурные инварианты;
- разрешённую область автономных изменений;
- запрещённые или требующие подтверждения действия.

### 3. `docs/autonomy/ROADMAP.md`

Хранит полный план дальнейшего развития в виде этапов и зависимостей.

Каждый этап должен содержать:

- результат этапа;
- критерий завершения;
- зависимости;
- состояние: `planned`, `active`, `blocked`, `done`, `superseded`;
- ссылки на более подробные спецификации или планы при их наличии.

Дорожная карта задаёт направление, а фактический код и проверки имеют более высокий приоритет при конфликте с устаревшей записью.

### 4. `docs/autonomy/RUNBOOK.md`

Описывает точный протокол одного автономного запуска, восстановление после прерывания, конфликт параллельных запусков и правила передачи состояния.

### 5. `docs/autonomy/DECISIONS.md`

Краткий журнал решений, которые влияют на будущие циклы:

- дата;
- решение;
- основание;
- затронутые ограничения;
- ссылка на подтверждающие изменения или проверки.

Записываются только решения, которые будущему запуску реально важно знать.

### 6. `docs/autonomy/ENTRY_PROMPT.md`

Готовая точка входа для обычного ChatGPT.

Она должна поддерживать два режима:

- первичная инициализация репозитория, если управляющего слоя ещё нет;
- продолжение разработки, если управляющий слой уже существует.

Промпт должен оставаться универсальным. Специфика проекта берётся из репозитория.

### 7. Существующие файлы состояния

`RUN_STATE.json`, `CHAMPION_STATE.json` и `AUTONOMOUS_LEARNING.md` сохраняются и получают формальный контракт. Создание дублирующих `STATE.md`, `NEXT.md` и похожих файлов не требуется.

## Иерархия источников истины

При каждом запуске ChatGPT обязан разрешать противоречия в таком порядке:

1. фактический GitHub: ветки, HEAD, PR, файлы, текущие результаты проверок;
2. `RUN_STATE.json` после проверки его ссылок на реальные SHA;
3. `CHAMPION_STATE.json` после проверки его SHA и доказательств;
4. утверждённые спецификации и планы;
5. `docs/autonomy/ROADMAP.md`;
6. `AUTONOMOUS_LEARNING.md` и `docs/autonomy/DECISIONS.md`;
7. история текущего чата.

Если документ противоречит фактическому GitHub, документ считается устаревшим и обновляется в рамках безопасного цикла.

## Новый контракт `RUN_STATE.json`

Существующий файл расширяется без потери полезных полей.

Минимальные поля v1:

```json
{
  "protocol_version": 1,
  "project": "Ren472230/Sam-Sebe-RPG",
  "authoritative_branch": "integration/audit-results-v1",
  "authoritative_head": "<sha>",
  "phase": "<current phase>",
  "current_objective": "<one current objective>",
  "next_action": "<one concrete next action>",
  "blockers": [],
  "active_run": {
    "run_id": null,
    "status": "idle",
    "started_at_utc": null,
    "lease_expires_at_utc": null,
    "base_sha": null,
    "working_branch": null
  },
  "last_handoff": {
    "completed_at_utc": null,
    "result": null,
    "head_sha": null,
    "verification": [],
    "next_action": null
  },
  "human_gate": {
    "required": false,
    "reason": null
  }
}
```

Старые поля могут оставаться, если они всё ещё отражают полезную предметную информацию.

## Защита от параллельных запусков

`RUN_STATE.json` используется как лёгкая аренда выполнения.

При старте запуск:

1. читает актуальный файл и его blob SHA;
2. проверяет `active_run`;
3. если активная аренда ещё действует, завершает цикл без изменений кода и фиксирует конфликт в отчёте;
4. если аренда свободна или истекла, записывает новый `run_id`, время старта, срок аренды, базовый SHA и рабочую ветку;
5. запись выполняется через GitHub с проверкой исходного blob SHA;
6. конфликт записи означает, что другой запуск успел захватить аренду первым;
7. при завершении цикл переводит `active_run.status` в `idle` и записывает `last_handoff`.

Срок аренды по умолчанию – 90 минут. Нормально завершившийся цикл освобождает её сразу, поэтому следующий почасовой запуск может продолжить работу. Перед длительной серией проверок активный цикл может продлить аренду атомарным обновлением `RUN_STATE.json`. Если 90 минут истекли при состоянии `running`, новый запуск сначала сверяет рабочую ветку, её HEAD и последние изменения, фиксирует восстановление после прерывания и только затем захватывает новую аренду.

Такой механизм использует оптимистическую блокировку GitHub и снижает риск двух параллельных агентов, которые одновременно меняют один проект.

## Политика рабочих веток

Для пилота `agent/autonomous-project-protocol-v1` является постоянной рабочей веткой внедрения управляющего слоя. Она создана от актуального HEAD PR #53.

Следующий автономный цикл продолжает ветку, записанную в `active_run.working_branch` или `last_handoff`, если фактический GitHub подтверждает её актуальность. Новая дочерняя ветка создаётся только для изолированного эксперимента, конфликтующей работы или отдельного изменения, которое по правилам проекта должно иметь собственный PR. Причина и имя новой ветки сразу записываются в состояние.

`authoritative_branch` обозначает ветку проекта, относительно которой автономная работа должна сверять актуальность. Пока управляющий слой пилота не интегрирован, ею остаётся `integration/audit-results-v1`. После отдельного решения об интеграции ссылка обновляется на фактическую новую базу.

Для других репозиториев политика веток задаётся в `PROJECT_CHARTER.md` и `AGENTS.md`.

## Машина состояний одного запуска

### A. RECONCILE

- открыть репозиторий;
- проверить актуальные PR, ветки и HEAD;
- прочитать управляющие файлы;
- проверить, что записанные SHA существуют;
- выявить устаревшие сведения;
- захватить аренду выполнения.

### B. SELECT

Выбрать одну законченную единицу работы.

Порядок выбора:

1. безопасность, целостность данных, потеря пользовательского состояния;
2. красный обязательный технический контроль или подтверждённая регрессия;
3. блокирующая задача активного этапа;
4. следующая обязательная задача утверждённого плана;
5. минимальная законченная часть текущего продуктового этапа;
6. удобство использования и визуальная доводка после функциональной готовности;
7. необязательные улучшения после закрытия обязательных задач.

Если задача слишком велика для одного запуска, выбирается минимальная самостоятельная часть, после которой репозиторий остаётся в понятном и проверяемом состоянии.

### C. EXECUTE

- использовать рабочую ветку, подтверждённую состоянием и политикой веток;
- изучить существующие реализации перед изменением;
- при исправлении дефекта сначала сохранить доказательство причины;
- при новой функциональности работать по утверждённому плану;
- избегать лишнего рефакторинга;
- сохранять действующие архитектурные инварианты.

### D. VERIFY

- запустить минимальные профильные проверки;
- затем выполнить обязательные связанные проверки;
- для релизных утверждений использовать результаты одного точного HEAD;
- красный результат считается фактом и записывается как блокер;
- старые зелёные результаты нельзя переносить на новый HEAD без подтверждения.

### E. RECORD

После работы обновить только данные, которые действительно изменились:

- `RUN_STATE.json`;
- `CHAMPION_STATE.json`, если появился новый проверенный кандидат;
- `AUTONOMOUS_LEARNING.md`, если получен новый полезный вывод;
- `ROADMAP.md`, если этап реально изменил состояние;
- `DECISIONS.md`, если принято долгоживущее решение.

### F. HANDOFF

Каждый запуск обязан оставить:

- что было целью;
- что реально изменено;
- точный итоговый HEAD;
- какие проверки выполнены и с каким результатом;
- подтверждённые блокеры;
- одно конкретное `next_action`;
- требуется ли действие владельца.

После этого аренда освобождается.

## Правила изменения дорожной карты

ChatGPT может самостоятельно:

- отметить выполненный этап при наличии доказательств;
- разбить слишком крупную задачу на проверяемые подзадачи;
- переставить ближайшие задачи, если новый блокер меняет зависимость;
- добавить найденный дефект;
- пометить устаревший пункт как `superseded` с объяснением;
- уточнить критерий завершения, если он был двусмысленным.

Отдельное подтверждение владельца требуется для:

- смены продуктовой цели;
- значительного расширения области проекта;
- разрушительных миграций данных;
- смены фундаментального стека без доказанной необходимости;
- действий с секретами, оплатой и внешними учётными записями;
- публикации релиза;
- слияния в `main`, пока владелец явно не изменит это правило.

## Универсальный входной промпт

`ENTRY_PROMPT.md` должен свести запуск к короткой команде вида:

> Возьми указанный репозиторий под автономный цикл разработки. Используй GitHub как источник истины. Если управляющий слой отсутствует, сначала создай его на изолированной ветке после анализа фактического проекта. Если он существует, восстанови состояние по `AGENTS.md` и `docs/autonomy/RUNBOOK.md`, захвати аренду в `RUN_STATE.json`, выбери одну приоритетную законченную задачу, выполни её, проверь результат на точном HEAD, обнови состояние и оставь одно конкретное следующее действие. Сохраняй правила владельца и обязательные подтверждения проекта.

Для конкретного проекта пользователь должен иметь возможность добавить только ссылку или имя репозитория.

## Первичная инициализация нового репозитория

Если управляющего слоя нет, первый запуск должен:

1. проверить реальный репозиторий, ветки, активные PR и последние изменения;
2. определить стек по manifest-файлам и коду;
3. восстановить продуктовую цель по README, документации и существующей реализации;
4. выявить тесты, CI, зависимости, деплой и внешние сервисы;
5. зафиксировать архитектурные инварианты;
6. сформировать `PROJECT_CHARTER.md` и `ROADMAP.md`;
7. создать `AGENTS.md`, `RUNBOOK.md`, `DECISIONS.md`, `ENTRY_PROMPT.md`;
8. создать или мигрировать машинное состояние;
9. оставить первый `next_action`;
10. начать продуктовую реализацию только после успешной проверки управляющего слоя и действующих проектных ограничений.

Первый этап внедрения:

1. добавить `AGENTS.md`;
2. добавить `docs/autonomy/PROJECT_CHARTER.md`;
3. добавить `docs/autonomy/ROADMAP.md`;
4. добавить `docs/autonomy/RUNBOOK.md`;

6. добавить `docs/autonomy/ENTRY_PROMPT.md`;

8. синхронизировать его с фактическим состоянием PR #53;
9. формально описать роль `CHAMPION_STATE.json` и `AUTONOMOUS_LEARNING.md`;
10. добавить проверки структуры управляющего слоя.

## Проверки управляющего слоя

В пилоте нужен небольшой автоматический контракт, который проверяет:

- обязательные файлы существуют;
- `RUN_STATE.json` является валидным JSON;
- `protocol_version == 1`;
- обязательные поля состояния присутствуют;
- `next_action` содержит одно конкретное действие;
- `AGENTS.md` ссылается на `RUNBOOK.md`;
- дорожная карта содержит хотя бы один активный или следующий этап;
- файлы не разрешают автоматическое слияние в `main` вопреки текущему правилу владельца.

Эти проверки относятся к управляющему слою и не должны менять игровую архитектуру.

## Почасовой запуск

После подтверждения двух последовательных ручных циклов без конфликта состояния можно подключить повторяющуюся задачу ChatGPT один раз в час.

Каждый плановый запуск выполняет тот же `ENTRY_PROMPT.md` и ограничивается одной законченной единицей работы.

Если предыдущий цикл сохранил активную аренду, новый запуск выполняет только сверку состояния и безопасно завершает работу без параллельного изменения кода.

## Критерии успеха пилота

Версия v1 считается работоспособной, если:

1. новый чат без истории проекта может восстановить фактическое состояние из репозитория;
2. для запуска достаточно имени репозитория и входного промпта;
3. два последовательных ручных цикла корректно продолжают друг друга;
4. состояние после каждого цикла содержит точный итоговый SHA и одно следующее действие;
5. устаревший `RUN_STATE.json` обнаруживается и исправляется по фактическому GitHub;
6. параллельный запуск безопасно останавливается при занятой аренде;
7. обязательные проверки относятся к точному текущему HEAD;
8. `main` остаётся защищённым от автономного слияния;
9. после пилота тот же каркас можно перенести в другой репозиторий заменой только проектной части `PROJECT_CHARTER.md` и `ROADMAP.md`.

## Этапы внедрения

### Этап 1 – управляющий слой

Создать файлы протокола, мигрировать состояние и добавить структурные тесты.

### Этап 2 – ручной автономный цикл

Запустить два последовательных цикла на реальной задаче `Sam-Sebe-RPG`, проверить передачу состояния, выбор следующей задачи и восстановление после нового запуска.

### Этап 3 – повторяющаяся задача

После подтверждения этапа 2 создать почасовую задачу ChatGPT с минимальным входным промптом.

### Этап 4 – универсализация

Проверить протокол на втором репозитории. Убрать из универсальной части всё, что оказалось специфичным для `Sam-Sebe-RPG`.

## Риски и защита

### Дрейф цели

Защита: `PROJECT_CHARTER.md` имеет более высокий смысловой приоритет, чем вновь придуманное улучшение. Изменение цели требует владельца.

### Устаревшее состояние

Защита: каждый запуск начинает с фактической сверки GitHub. SHA в документах всегда проверяются.

### Бесконечная доводка

Защита: одна законченная единица работы за цикл, явный активный этап и приоритет обязательных задач над косметикой.

### Повтор работы

Защита: `last_handoff`, точный HEAD, журнал решений и проверка существующей реализации перед изменениями.

### Параллельные циклы

Защита: аренда в `RUN_STATE.json` и запись по актуальному blob SHA.

### Ложная готовность

Защита: статус готовности определяется свежими проверками на точном HEAD. Человеческие качественные проверки остаются отдельным состоянием, пока человек их реально не выполнил.

## Итоговое решение

Для пилота выбирается минимальный управляющий слой поверх уже существующих автономных артефактов проекта. Он должен сделать репозиторий самодостаточным для восстановления контекста новым запуском ChatGPT и подготовить безопасный почасовой цикл без зависимости от истории чата.
