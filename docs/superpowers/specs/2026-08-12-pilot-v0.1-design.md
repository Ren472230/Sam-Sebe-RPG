# Pilot v0.1 — Design Specification

## Product hypothesis

Pilot v0.1 tests one thing: whether a player enjoys freely experimenting with a small persistent world when the game recognizes sustained behavior and turns it into personal mechanical progression.

The pilot is successful only if the player voluntarily performs unprompted experiments, understands the causal link between behavior and progression, and wants to test the new ability after it appears.

## Scope

Pilot v0.1 is a single-player founder vertical slice used before multiplayer expansion.

Included:
- 3 locations: yard/workshop, square/tavern, river/forest edge;
- 3 NPCs;
- 1 animal type: ravens;
- 4–6 resources;
- a small canonical action vocabulary;
- deterministic action validation and resolution;
- persistent SQLite state;
- append-only gameplay event log;
- behavior aggregation;
- one complete Behavior → Achievement → Ability loop;
- a constrained mechanic compiler/validator;
- optional natural-language parser behind an interface;
- Discord adapter only after the core loop works locally.

Explicitly excluded:
- classes, levels, fixed skill trees;
- quest system;
- factions/organizations;
- full combat/PvP;
- complex economy;
- procedural world generation;
- vector database/RAG;
- autonomous LLM world mutation;
- web frontend;
- MMO infrastructure;
- paid external infrastructure.

## Core loop

1. Player observes world state.
2. Player attempts an action.
3. Input becomes a CanonicalAction.
4. Simulation validates affordances and preconditions.
5. Deterministic resolver produces an ActionResult.
6. Resolver commits state mutation.
7. EventStore appends an ActionEvent.
8. BehaviorAnalyzer updates the player behavior profile.
9. ProgressionService evaluates progression rules.
10. When evidence is sufficient, an achievement and ability are unlocked.
11. Player can immediately use the ability and test its boundaries.

## Authoritative-state rule

Only the deterministic simulation layer may mutate authoritative world state.

LLM output, when later enabled, is always a proposal:

`free text -> parsed proposal -> validation -> deterministic execution`

No LLM component can directly write game state, inventory, relations, progression, or event history.

## Canonical action model

The first action families are:
- LOOK
- MOVE
- TAKE
- DROP
- GIVE
- USE
- THROW
- FEED
- WAIT

A CanonicalAction contains:
- actor_id;
- action_type;
- target_id (optional);
- item_id (optional);
- destination_id (optional);
- modifiers (small validated dictionary);
- source_text (optional, non-authoritative).

## Action event model

Every resolved attempt produces an event, including failures.

ActionEvent contains:
- event_id;
- world_time;
- actor_id;
- action_type;
- target_id/item_id/location_id when relevant;
- success;
- result_code;
- behavior_tags;
- numeric evidence useful to progression;
- compact human-readable summary.

The event log is gameplay evidence. Progression never relies on LLM memory or prose summaries.

## Behavior Engine v0

The first engine is deterministic and rule-based. It aggregates evidence from ActionEvent records.

For throwing it tracks:
- total valid attempts;
- successful hits;
- distinct targets;
- distinct projectile items;
- distinct locations;
- aimed attempts;
- successful aimed attempts.

Progression requires more than repetition. The initial unlock rule requires a minimum amount of activity plus variation and competence.

## First progression branch

### Achievement: «Рука помнит дугу»

Behavior basis: sustained precision throwing with improvised objects.

Pilot unlock evidence:
- at least 12 valid THROW events;
- at least 5 successful throws;
- at least 3 distinct targets;
- at least 2 projectile types;
- at least 2 locations.

These thresholds are intentionally accelerated for founder testing.

### Ability: Aimed Throw

The ability unlocks an explicit action variant rather than only adding a hidden stat.

Mechanic:
- action family: THROW;
- modifier: aimed=true;
- accuracy bonus: +10 percentage points;
- stamina surcharge: +1 when stamina is introduced;
- only works with items tagged improvised_projectile.

For the first implementation, stamina can be omitted while the action variant and accuracy change are implemented.

## Mechanic compiler v0

The first version is intentionally not generative. It validates predefined mechanic specs against a whitelist so the boundary is implemented before AI-assisted mechanic proposals are added.

Allowed primitives:
- MODIFY_ACCURACY;
- MODIFY_RANGE;
- MODIFY_COST;
- MODIFY_QUALITY;
- MODIFY_RELATION_GAIN;
- UNLOCK_ACTION_VARIANT;
- CONDITIONAL_MODIFIER;
- REPUTATION_TAG.

Pilot limits include:
- accuracy bonus <= 15 percentage points;
- range bonus <= 10%;
- cost reduction <= 20%;
- relation gain modifier <= 25%.

Unknown primitives or values outside limits are rejected.

## Minimal world

Locations:
- workshop_yard;
- village_square;
- river_edge.

NPCs:
- mira_craftswoman at workshop_yard;
- oren_innkeeper at village_square;
- kaspar_forager at river_edge.

Animals:
- raven_1 and raven_2, represented by deterministic trust/fear state.

Resources/items include several stones plus food and simple utility items. At least two item types must be throwable so the first progression branch can test variation.

## Persistence

SQLite is the only database.

Minimum tables:
- world_meta;
- entities;
- player_state;
- inventory;
- relations;
- action_events;
- behavior_profiles;
- achievements;
- abilities.

For v0.1, schema simplicity is preferred over generic ECS abstractions.

## Time and persistence model

The world uses discrete world ticks. WAIT advances time. Later, real elapsed time can be converted to lazy catch-up ticks when the process receives the next command.

The first implementation does not run continuous background simulation.

## Interfaces

Core simulation must not depend on Discord or an LLM.

Primary service boundary:

`GameService.execute(CanonicalAction) -> ActionResult`

Adapters:
- Local CLI / scripted scenario (first);
- Parser interface (rule-based first, LLM implementation later);
- Discord adapter (after core verification).

## Error handling

Invalid actions are gameplay results, not exceptions.

Examples:
- ITEM_NOT_OWNED;
- TARGET_NOT_PRESENT;
- INVALID_DESTINATION;
- ITEM_NOT_THROWABLE;
- ACTION_NOT_UNLOCKED.

Exceptions are reserved for programmer/data corruption errors.

## Testing strategy

Tests cover behavior, not implementation details.

Required first tests:
- cannot take an item from another location;
- taking an item mutates inventory and event log;
- throwing consumes/moves the correct item state and logs success/failure;
- deterministic resolution is reproducible with seeded RNG;
- failed actions still produce events where appropriate;
- behavior profile aggregates throw evidence correctly;
- achievement does not unlock from repetition alone;
- achievement unlocks when frequency, variation, and competence thresholds are satisfied;
- ability is persisted and immediately usable;
- mechanic validator rejects unsafe specs;
- reloading the database preserves authoritative state and progression.

## Pilot success criteria

A founder session of roughly 30–60 minutes should produce:
- at least 5 unprompted experimental actions;
- a comprehensible personal progression event;
- immediate attempts to reuse/test the unlocked ability;
- clear perception that the ability followed from the player's behavior.

Technical baseline:
- no direct LLM state mutations;
- no mechanic outside whitelist;
- deterministic tests pass under a fixed seed;
- restart does not lose state.

## Implementation order

1. Python package and tests.
2. Domain models and SQLite schema.
3. Minimal world bootstrap.
4. Deterministic GameService for LOOK/MOVE/TAKE/DROP/THROW/WAIT.
5. Event log.
6. Behavior aggregation.
7. Throwing achievement and Aimed Throw.
8. Mechanic validator boundary.
9. Local playable CLI.
10. FEED/GIVE/USE and raven trust if core remains small.
11. Natural-language parser interface/implementation.
12. Discord adapter.

## Architecture decisions

- Python 3.12+.
- Standard library first; pytest is the only initial development dependency.
- sqlite3 directly, no ORM.
- dataclasses/enums for domain models.
- one process.
- no Docker requirement.
- no paid service requirement.

## Definition of Pilot v0.1 working model

The repository contains a documented setup and a local command that starts a persistent world, lets a player inspect/move/take/throw/wait, records events, detects the first emergent specialization, unlocks Aimed Throw, persists it across restarts, and demonstrates the loop through automated tests and a short scripted play scenario.
