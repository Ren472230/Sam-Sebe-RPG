# Sam-Sebe RPG — Capital Audit

Date: 2026-08-13
Status: Pilot v0.1 deterministic core implemented and verified locally

## Executive verdict

Проект имеет сильное и редкое продуктово-игровое ядро, но его нельзя оценивать как «AI RPG». Его реальный клин — **социальный persistent-мир, который наблюдает за поведением игроков, запоминает последствия и превращает повторяющийся стиль жизни в личные игровые механики**.

Самый сильный продуктовый образ:

> Ты приходишь почти никем. Мир смотрит на то, как ты живёшь. Пустые разделы персонажа постепенно заполняются тем, что ты действительно заслужил своим поведением.

Самый большой риск: scope creep. Почти каждая идея проекта — NPC-жизнь, экономика, газета, забывание, недвижимость, Discord-локации, relationship memory, визуальная новелла, генерация механик — сама по себе способна стать отдельной системой. Поэтому развитие должно идти через последовательные доказательства core loop, а не через строительство «полного мира».

## 1. Что зафиксировано как канон

### Product fantasy

- один общий persistent-мир;
- мир существует независимо от конкретного игрока;
- все игроки влияют на одну каноническую историю;
- NPC помнят взаимодействия и продолжают жить без игрока;
- поведение игрока порождает достижения;
- достижения открывают навыки, статы, активные способности и потенциально новые механики;
- заранее выбранного класса нет;
- история и механические последствия важнее бесконечной генерации текста.

### Presentation fantasy

На старте игра должна ощущаться как визуальная новелла:

- большой визуальный слой сцены;
- красивый персонаж в сцене;
- отдельное окно реплик;
- выбор действия + возможность свободного ввода;
- RPG-меню: персонаж, навыки, таланты, характеристики, достижения, отношения, инвентарь;
- в начале почти все разделы пусты;
- весь presentation layer — персонажи, локации, рамки, эффекты, меню — выполнен в одной premium ASCII/символьной эстетике с динамическим цветом.

### World rules

- мир синхронизирован с реальным временем;
- каждое утро публикуется газета/сводка мира;
- authoritative state хранится в БД;
- LLM не проводит транзакции и не является источником истины;
- долгоживущая память хранит компактные структурированные факты, а не сырой бесконечный чат;
- действует Закон Забвения: детали памяти ослабевают со временем, а важность и повторное подкрепление замедляют забывание;
- стартовый масштаб — одна деревня/маленький регион;
- стартовый капитал может быть одинаковым для всех игроков;
- игроки потенциально создают жильё, бизнесы и социальные места.

## 2. Текущее техническое состояние

Pilot v0.1 теперь реализует:

- Python 3.12+ package;
- SQLite authoritative persistence;
- WAL + busy timeout для локальной конкурентности;
- 3 локации;
- 3 NPC;
- 2 ворона;
- базовые предметы и цели;
- `LOOK`, `MOVE`, `TAKE`, `DROP`, `THROW`, `WAIT`;
- atomic transaction per action;
- append-only `action_events`;
- seeded deterministic RNG;
- BehaviorAnalyzer;
- anti-grind progression evidence;
- achievement `hand_remembers_arc`;
- ability `aimed_throw`;
- mechanic whitelist + limits;
- deterministic Russian parser;
- local CLI;
- reproducible demo scenario;
- 32 automated tests.

Это уже не документальная концепция: ключевой Behavior → Achievement → Mechanic цикл выполняется end-to-end.

## 3. Что Pilot v0.1 правильно НЕ делает

Это полезные ограничения, их пока нельзя снимать одновременно:

- нет LLM-зависимости;
- нет Discord-зависимости в core;
- нет web frontend в simulation layer;
- нет классов и фиксированных skill trees;
- нет сложной экономики;
- нет автономной генерации канонических механик;
- нет MMO-инфраструктуры;
- нет платной инфраструктуры;
- нет vector DB/RAG.

## 4. Главный архитектурный вывод после аудита Discord

Есть три возможных presentation-подхода.

### A. Только Discord bot + Components V2

Плюсы:
- максимально нативно;
- быстрый MVP;
- кнопки, select menus, text inputs, media gallery;
- хорошо подходит для газет, уведомлений, локационных сообщений и быстрых действий.

Минусы:
- ограниченный визуальный контроль;
- трудно добиться ощущения полноценной визуальной новеллы;
- сцена, персонаж и RPG HUD будут постоянно упираться в layout Discord сообщений.

Вердикт: хороший companion layer, слабый основной игровой экран.

### B. Discord Activity + bot companion — РЕКОМЕНДУЕТСЯ

Discord Activities — официальные web-приложения, работающие внутри Discord на desktop/mobile/web. Это позволяет сделать настоящий VN/ASCII экран с кастомным layout, а bot оставить для социальных поверхностей мира.

Распределение ответственности:

- **Activity**: сцена, ASCII-персонаж, диалог, RPG-меню, свободный ввод, локальный HUD;
- **Bot / Components V2**: каналы-локации, morning newspaper, world alerts, приглашения, быстрые действия;
- **Backend**: auth, simulation API, event stream;
- **GameService**: единственный authoritative resolver;
- **SQLite**: каноническое состояние первого MVP.

Плюсы:
- визуальная новелла действительно остаётся внутри Discord;
- полный контроль над ASCII-визуалом;
- не нужно превращать message components в псевдо-игровой движок;
- социальный слой Discord сохраняется как часть самой игры.

Минусы:
- появляется web frontend;
- Activity требует отдельной доставки frontend/backend;
- нужно решить синхронизацию Activity с общим миром.

Вердикт: лучший fit с продуктовым видением.

### C. Внешний web-клиент + Discord bot

Плюсы:
- максимальная свобода UI;
- простая обычная web-разработка.

Минусы:
- нарушает сильную идею «игра живёт в Discord»;
- добавляет переходы и friction;
- хуже социальное распространение внутри сервера.

Вердикт: fallback, а не целевой путь.

## 5. Целевая архитектура v0.2–v0.4

```text
Discord Activity (VN/ASCII) ─┐
                             ├─> Application API ─> GameService ─> SQLite
Discord Bot / Components V2 ─┘                        │
                                                      ├─> ActionEvent log
                                                      ├─> Behavior Engine
                                                      ├─> Progression Engine
                                                      └─> World Clock

LLM Gateway ──> structured proposal ──> validator ──> GameService
                dialogue/narrative only      ↑
                                             │
Memory / Forgetting Engine ──────────────────┘
```

Ключевой принцип: Activity, bot и LLM — адаптеры. Они не получают отдельной «версии мира» и не имеют права напрямую мутировать таблицы gameplay state.

## 6. Технические риски

### Critical

1. **Scope creep** — главный риск проекта.
2. **Social cold start** — multiplayer без активных людей выглядит пустым.
3. **LLM authority leak** — если модель сможет «уговорить» игру провести незаконную транзакцию, доверие к миру исчезнет.
4. **Moderation / romance / minors** — открытый social RP требует отдельной политики безопасности и реального moderation tooling.
5. **Emergent progression balance** — генерация слишком частых/смешных достижений превратит USP в AI-slop.

### High

6. SQLite допускает много readers, но только одного writer одновременно; для 10–25 тестеров это приемлемо при коротких транзакциях, WAL и busy timeout. При росте нагрузки нужен instrumentation before migration, а не преждевременный Postgres.
7. NPC simulation может стать крупнейшим LLM-cost центром. NPC не должны «думать текстом» каждую минуту. Большинство фоновой жизни должно считаться дешёвой simulation/logical scheduling.
8. Memory compression должна быть детерминированно связана с evidence/provenance, иначе мир начнёт переписывать собственную историю.

## 7. Что НЕ надо строить сейчас

- много биомов;
- полноценную боёвку;
- сложный crafting;
- десятки профессий;
- огромный lore bible;
- marketplace;
- mobile app;
- собственную MMO server architecture;
- vector memory «на всякий случай»;
- procedural generation всей карты;
- платёжную систему;
- сложный admin dashboard.

## 8. Следующая работа по ценности

### P0 — Multiplayer identity + location occupancy contract

Перед Discord нужен минимальный контракт:

- `discord_user_id -> player_id`;
- несколько игроков в одной БД;
- location membership;
- optimistic/serialized action handling;
- тест двух игроков, взаимодействующих с одним объектом;
- корректная гонка за один предмет: получить его может только один.

Почему это P0: без доказанной мультипользовательской каноничности нельзя безопасно подключать Discord и социальный UI.

### P1 — Discord Activity visual shell

После P0:

- один экран сцены;
- premium ASCII фон;
- один ASCII NPC;
- dialogue window;
- choice chips + free text;
- RPG drawer с почти пустыми разделами;
- mocked/real backend view model;
- mobile-first layout.

### P2 — Bot companion

- канал-локация mapping;
- `/enter`, `/where`, `/look` или эквивалентные interactions;
- morning newspaper placeholder;
- Components V2 cards;
- Activity launch entry point.

### P3 — NPC dialogue + structured intent

LLM только после того, как deterministic multiplayer path работает без него.

### P4 — World clock + daily paper + Forgetting v0

Сначала event summarization/evidence, потом художественная генерация.

## 9. Внутренние kill / go criteria для закрытой альфы

Это не рыночные benchmarks, а предлагаемые founder decision gates.

GO, если за неделю на 10–20 тестерах:

- игроки сами пробуют действия, которые им не предлагали;
- возникают хотя бы несколько историй, которые дизайнер не писал заранее;
- игроки замечают причинную связь «моё поведение → новая возможность»;
- игроки возвращаются из любопытства к миру, а не только по просьбе тестера;
- возникает хотя бы одна социальная зависимость: обмен, договорённость, конфликт, совместный план, место или роль;
- люди пересказывают произошедшее человеческим языком как историю, а не как «ответ нейросети».

KILL/RETHINK, если после нескольких итераций:

- игроки используют мир как обычный чат с NPC;
- свободные действия не вызывают осмысленных механических последствий;
- progression воспринимается как случайная награда;
- world state регулярно противоречит сам себе;
- игрокам безразлично, что происходило, пока они были офлайн;
- социальная часть не создаёт причин возвращаться.

## 10. Коммерческий вывод

Коммерческий потенциал проекта остаётся высоким именно как **культовый social world**, а не как «генеративная RPG с бесконечным контентом».

Вероятный moat при успехе — не модель и не текстовый генератор. Moat образуется из:

- общей истории конкретного мира;
- социальных связей;
- заработанной игроками идентичности;
- накопленных структурированных последствий;
- уникальных emergent mechanics;
- community lore;
- привычки возвращаться к ежедневной жизни мира.

То есть ценность растёт со временем использования — хороший признак для community-driven продукта.

## 11. Итоговое решение аудита

1. Pilot v0.1 сохранить как чистое deterministic ядро.
2. Не переписывать его под frontend.
3. Следующий engineering slice — multiplayer identity/concurrency.
4. Целевой presentation layer — Discord Activity + bot companion.
5. Premium ASCII VN — не декорация, а основной UX диалогов и персонального RPG состояния.
6. Bot-каналы остаются физическими/социальными пространствами мира и каналом world events.
7. LLM подключать только за typed/validated boundary.
8. SQLite оставить до появления измеренного write-contention; WAL уже включён.
9. Закрытую альфу проводить на одной маленькой деревне.
10. Главная метрика — emergent stories with consequences.
