# Регламент автономного запуска Sam-Sebe-RPG

## Вход

Каждый новый запуск начинает работу с фактического GitHub, затем читает `AGENTS.md`, `AUTONOMY_SYSTEM.json`, этот регламент, `PROJECT_CHARTER.md`, `RUN_STATE.json`, `CHAMPION_STATE.json`, активный этап `ROADMAP.md` и связанный план в `docs/superpowers/`.

## Жёсткий барьер аренды

**До успешной записи аренды запрещены любые изменения** кода, конфигурации, документации, веток и проектного состояния, кроме атомарной записи самой аренды в `RUN_STATE.json`.

**Сверка до захвата аренды выполняется только на чтение.** Найденные устаревшие записи и требуемые исправления фиксируются как результат сверки и применяются только после подтверждения владения арендой.

После записи аренды повторно прочитай `RUN_STATE.json`. Остальные изменения разрешены только если файл подтверждает твой `run_id`, статус `running` и ожидаемую рабочую ветку.

## 1. RECONCILE

До захвата аренды выполняй только чтение:

1. Проверь PR #53, `integration/audit-results-v1`, пилотную рабочую ветку и их текущие SHA.
2. Проверь результаты обязательных проверок для фактического авторитетного HEAD.
3. Сравни факты с `RUN_STATE.json`, `CHAMPION_STATE.json` и дорожной картой.
4. Составь список подтверждённо устаревших сведений для исправления после аренды.
5. Проверь `active_run`.

### Аренда

Если `active_run.status` равен `running` и срок ещё действует, второй запуск прекращает конкурентные изменения.

Если аренда свободна или истекла:

1. прочитай текущий blob SHA `RUN_STATE.json`;
2. при истёкшей аренде восстанови фактическое состояние рабочей ветки только на чтение;
3. создай уникальный `run_id`;
4. подготовь `status: running`, время старта, срок аренды на 90 минут, `base_sha` и рабочую ветку;
5. атомарно обнови файл с проверкой исходного blob SHA;
6. повторно прочитай `RUN_STATE.json` и подтверди, что активна именно твоя аренда.

Конфликт записи означает, что другой запуск захватил аренду первым. В таком случае прекрати запуск без других изменений.

### Восстановление после истёкшей аренды

Если срок истёк при `status: running`:

1. проверь записанную рабочую ветку только на чтение;
2. сравни её фактический текущий HEAD с `base_sha` и `last_handoff.work_head_sha`;
3. изучи последние изменения и проверки;
4. определи, была ли работа частично завершена;
5. подготовь факт восстановления для будущей записи;
6. захвати новую аренду;
7. после подтверждения аренды запиши факт восстановления, если он влияет на будущую работу.

## 2. SELECT

После подтверждения аренды сначала синхронизируй подтверждённо устаревшие управляющие сведения, найденные на этапе сверки, если это требуется для текущего цикла.

Затем выбери одну законченную единицу работы по приоритету:

1. безопасность и сохранность данных;
2. красная обязательная проверка или воспроизводимая регрессия;
3. блокер активного этапа;
4. следующая задача утверждённого плана;
5. минимальная самостоятельная часть текущего этапа;
6. удобство и визуальная доводка после функциональной готовности.

Текущий план стабилизации является главным техническим ориентиром, пока факты GitHub подтверждают его актуальность.

Перед выполнением запиши `current_objective` и `next_action` так, чтобы их можно было понять без истории чата.

## 3. EXECUTE

- Работай в `agent/autonomy-pilot-v0.1`, пока состояние и GitHub подтверждают эту политику.
- Изучи затрагиваемую реализацию и проверки до изменения.
- Для дефекта используй существующее воспроизводимое красное доказательство или получи новое.
- Исправляй причину минимальным изменением.
- Сохраняй архитектурные инварианты проекта.
- Не маскируй браузерный дефект телепортацией, отключением столкновений, изменением скорости игры, глобальным увеличением тайм-аутов или повторами ради зелёного результата.
- Не выполняй слияние в `main`.

## 4. VERIFY

1. Запусти профильную проверку изменённого поведения.
2. Если она зелёная, запусти связанные проверки текущего этапа.
3. Сохрани точный SHA рабочего результата, на котором реально выполнялись проверки.
4. Записывай идентификаторы GitHub Actions, SHA и результат.
5. Красный обязательный результат становится блокером.
6. Недоступную проверку помечай как недоступную, а не как пройденную.

## 5. RECORD

Обновляй по фактам:

- `RUN_STATE.json` после каждого цикла;
- `CHAMPION_STATE.json` только при изменении кандидата или доказательств;
- `ROADMAP.md` при реальном изменении этапа;
- `AUTONOMOUS_LEARNING.md` при новом переносимом выводе;
- `DECISIONS.md` при долгоживущем решении.

## Семантика SHA передачи

`last_handoff.work_head_sha` хранит точный SHA проверенного рабочего результата до финального мета-коммита состояния.

Фактический текущий HEAD рабочей ветки после обновления `RUN_STATE.json` каждый новый запуск получает напрямую из GitHub. SHA коммита, который меняет `RUN_STATE.json`, нельзя атомарно записать внутрь того же файла: изменение файла создаёт новый SHA и делает такую самоссылку бесконечной.

Коммиты состояния после `work_head_sha` допустимы. При следующей сверке агент обязан получить фактический текущий HEAD, изучить разницу после `work_head_sha` и убедиться, что она соответствует ожидаемой передаче или последующим фактическим изменениям.

## 6. HANDOFF

Перед завершением оставь в `last_handoff`:

- завершённую цель;
- реальные изменения;
- точный `work_head_sha` проверенного рабочего результата;
- фактически выполненные проверки;
- блокеры;
- ровно одно ближайшее действие;
- необходимость решения владельца.

После успешной передачи:

1. атомарно установи `active_run.status: idle` и очисти временные поля аренды;
2. сохрани `last_handoff` с `work_head_sha`;
3. повторно прочитай `RUN_STATE.json` и подтверди, что аренда освобождена и передача записана;
4. отдельно получи из GitHub фактический текущий HEAD рабочей ветки для итогового отчёта.

## Человеческая контрольная точка

Остановись перед слиянием в `main`, публикацией релиза, разрушительной миграцией, изменением секретов или оплаты, сменой фундаментального стека и существенным изменением продуктовой цели.
