# Sam-Sebe-RPG – V1 Quality Contract

Дата фиксации: 2026-09-16
Статус: обязательный контракт качества автономной разработки текущего браузерного vertical slice.

## Назначение

Этот контракт задаёт конечную планку качества V1 текущего демонстрационного среза Sam-Sebe-RPG. Автономная разработка должна закрывать измеримые красные Quality Gates, а не бесконечно расширять проект.

Текущая V1 – цельный и устойчивый демонстрационный срез маленькой живой деревни из действующего PROJECT_CHARTER. Полноценная содержательно завершённая RPG находится вне текущей V1.

Средний Quality Score не может перекрыть красный обязательный Hard Gate.

## Статусы проекта

- `IN_DEVELOPMENT` – хотя бы один технический Hard Gate красный, неизвестен или заблокирован.
- `TECHNICALLY_READY_AWAITING_HUMAN_QA` – все технические Hard Gates зелёные на одном доказанном кандидате и Quality Score >= 90/100.
- `V1_DONE` – техническая планка пройдена и владелец явно подтвердил Human Experience Gate.

При `TECHNICALLY_READY_AWAITING_HUMAN_QA` запрещено автономно добавлять новые квесты, NPC, системы, локации, механику, декоративные экраны и расширение художественного scope. Разрешены только проверка свежей регрессии и исправление доказанного дефекта.

При `V1_DONE` регулярные задачи не развивают текущую V1 дальше. Новый контент относится к следующей версии и требует отдельного решения владельца.

## Зафиксированная граница V1

В V1_REQUIRED входят только уже утверждённые элементы текущего PROJECT_CHARTER:

- Start Village и таверна;
- Living World;
- Living NPC;
- Social World;
- Living Conversation;
- причинно ограниченная передача знаний;
- физическое движение и пространственное взаимодействие игрока;
- TAKE / GIVE / WAIT;
- квест Орена с дровами;
- бытовая ситуация Миры и Каспара;
- прибытие Талена и гостеприимный цикл с хлебом;
- сохранение состояния SQLite;
- браузерный Phaser-клиент;
- текущий SVG-набор как достаточное production-facing представление V1;
- автоматические серверные, браузерные, Windows и воспроизводимые проверки.

Расширение этой границы автономно запрещено.

## Hard Gates V1

### RQ-H01 – Seven Required Release Gates on One SHA

На одном точном итоговом candidate SHA должны быть GREEN все семь обязательных проверок PROJECT_CHARTER:

1. `Visual Forge Gate`;
2. `Stream Slice Gate`;
3. `Prototype Web CI`;
4. `Playable Candidate Gate`;
5. `Windows Compatibility Gate`;
6. `Living World Integration Gate`;
7. `Release Reproducibility Gate`.

Старый зелёный прогон другого SHA не является доказательством.

### RQ-H02 – Repeated Browser Route Stability

Критический Stream Slice должен пройти минимум 3 последовательных раза на одном и том же candidate SHA.

Обязательное условие: маршрут использует реальное клавиатурное/игровое управление и фактическую физику. Запрещены телепортация, прямое выставление state, отключение столкновений, искусственное увеличение радиуса взаимодействия, огромные timeout и бесконечные retry ради зелёного результата.

Любой один красный повтор сбрасывает серию для этого SHA.

### RQ-H03 – Canonical Vertical Slice Completion

Реальный браузерный маршрут V1 должен пройти утверждённый демонстрационный срез без dev-вмешательства и прямой подмены состояния.

Проверка должна доказать доступность и целостность ключевых сценариев текущего scope:

- старт и управление в Start Village;
- физический вход/выход из таверны;
- TAKE / GIVE / WAIT;
- квест Орена с дровами;
- сценарий Миры и Каспара;
- прибытие Талена и гостеприимный цикл с хлебом;
- минимум один реальный Living Conversation путь;
- продолжение игры после обязательных переходов без softlock.

Если конкретный сценарий намеренно исключён из V1, это требует изменения PROJECT_CHARTER владельцем, а не самостоятельного понижения требования агентом.

### RQ-H04 – Living Systems Integrity

Должны быть зелёными детерминированные доказательства для:

- Living World;
- Living NPC;
- Social World;
- Living Conversation;
- причинной передачи знаний с происхождением;
- запрета превращения неподтверждённого утверждения игрока в объективный факт мира.

Языковая модель не должна получать прямую власть над физическим каноническим состоянием мира.

### RQ-H05 – Persistence / Reload Integrity

Обязательный V1 state должен переживать сохранение и перезапуск/перезагрузку в пределах утверждённой архитектуры SQLite.

PASS требует:

- сохранённые факты мира восстанавливаются;
- инвентарь/локации/отношения, затронутые обязательным срезом, не откатываются самопроизвольно;
- причинная память/знания не теряют доказанное происхождение;
- существующие совместимые сохранения не разрушаются текущим кандидатом;
- проверка относится к точному candidate SHA.

### RQ-H06 – Runtime Integrity / No Critical Blockers

Для технической готовности требуется:

- 0 известных подтверждённых P0 дефектов;
- 0 известных подтверждённых P1 дефектов главного игрового пути;
- 0 uncaught browser/page errors на каноническом маршруте;
- 0 softlock основного среза;
- 0 обязательных переходов, зависящих от ручного вмешательства разработчика.

Известный красный required gate автоматически означает, что этот gate не GREEN.

### RQ-H07 – Visual / Input Usability

На основных поверхностях текущего V1 не должно быть блокирующих UX/визуальных дефектов.

Минимальная проверка:

- desktop основной режим;
- 390x844 portrait fallback;
- 844x390 coarse-pointer landscape fallback.

PASS требует:

- отсутствует блокирующее горизонтальное переполнение;
- обязательные элементы не перекрывают друг друга;
- обязательные controls не скрыты CSS cascade;
- основной текст и interaction hints читаемы;
- модальные состояния не блокируют дальнейший путь;
- primary actions доступны;
- мобильное управление не ломает desktop keyboard flow.

Эстетическое качество окончательно подтверждается Human Gate, а не самим агентом.

### RQ-H08 – Reproducibility and Supported Environment

PASS требует зелёных доказательств на текущем кандидате для:

- воспроизводимой установки зависимостей;
- production web build;
- Windows Compatibility Gate;
- Release Reproducibility Gate;
- запуска backend/API и SQLite в предусмотренном release-контуре;
- отсутствия зависимости от локальных dev-файлов/секретов для обязательного демонстрационного пути.

### RQ-H09 – Human Experience Gate

После технической готовности владелец проводит минимум один полный человеческий плейтест текущего vertical slice на целевой среде.

Для PASS требуется явное подтверждение владельца, что:

- управление понятно без технического вмешательства;
- ключевые игровые действия считываются;
- демонстрационный маршрут реально проходится;
- нет критического визуального/игрового дефекта, делающего опыт неприемлемым;
- состояние можно считать `V1_DONE`.

Автоматические тесты, screenshot review и собственная оценка агента не могут закрыть этот gate.

## Quality Score – 100 баллов

Quality Score считается только по доказанным подпунктам. `UNKNOWN` даёт 0 до появления evidence. Итог округляется до целого.

### 1. Reliability – 30

- 14 – семь обязательных release gates GREEN на одном SHA, по 2 балла каждый;
- 6 – три последовательных Stream Slice PASS на том же SHA;
- 5 – 0 P0/P1 и 0 uncaught errors на главном пути;
- 5 – отсутствие softlock и ручной подмены state.

### 2. Core Gameplay – 25

- 10 – canonical vertical slice проходит полностью;
- 5 – физическая навигация Start Village / tavern стабильна;
- 5 – TAKE / GIVE / WAIT и квестовый путь работают реальным игровым способом;
- 5 – Mira/Kaspar + Talen hospitality сценарии доступны и не ломают продолжение игры.

### 3. Living World / Causality – 20

- 5 – Living World;
- 5 – Living NPC + Social World;
- 5 – Living Conversation;
- 5 – причинная передача знаний и provenance-инварианты.

### 4. UX / Visual – 15

- 7 – desktop основной режим;
- 4 – 390x844 fallback;
- 4 – 844x390 coarse-pointer fallback.

Каждый подпункт считается только при отсутствии блокирующего overflow/overlap/hidden-control/route-blocking issue на соответствующей поверхности.

### 5. Persistence / Compatibility – 10

- 5 – save/reload integrity;
- 3 – Windows compatibility;
- 2 – release reproducibility.

## Порог технической готовности

`TECHNICALLY_READY_AWAITING_HUMAN_QA` разрешён только если одновременно:

1. `RQ-H01..RQ-H08` = GREEN;
2. Quality Score >= 90/100;
3. все доказательства относятся к актуальному candidate SHA либо явно допустимому same-code publication SHA;
4. нет открытого `HUMAN_DECISION_REQUIRED`, влияющего на V1_REQUIRED.

`RQ-H09` переводит проект в `V1_DONE` только после явного подтверждения владельца.

## Правило выбора следующей автономной цели

Приоритет любого GAMEPLAY/VISUAL цикла:

1. свежий красный required release gate;
2. красный Hard Gate своей зоны;
3. доказанный P0/P1 дефект;
4. подпункт Quality Score ниже своего порога;
5. только после этого – реализация внутри уже зафиксированного V1_REQUIRED.

`SESSION_OBJECTIVE` обязан называть конкретный gate ID либо измеримый Quality Score submetric, который он закрывает/продвигает.

Запрещено выбирать новую функцию или косметическую полировку только потому, что она кажется полезной.

## Truthfulness и переходы состояния

- `GREEN` требует exact SHA + проверку/сценарий + результат.
- `RED` требует конкретный дефект или неуспешную проверку.
- `UNKNOWN` означает отсутствие свежего достаточного evidence.
- `PENDING_HUMAN` используется для Human Gate.
- Требования и веса нельзя автономно снижать ради достижения V1_DONE.
- Если проект уже `TECHNICALLY_READY_AWAITING_HUMAN_QA`, регулярный запуск не создаёт новую продуктовую работу при отсутствии свежей регрессии.
- Если проект уже `V1_DONE`, регулярный запуск завершает read-only проверку состояния и не создаёт новую работу V1.
