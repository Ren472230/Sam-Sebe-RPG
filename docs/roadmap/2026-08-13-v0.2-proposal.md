# v0.2 Proposal — Multiplayer Canonical World

## Why this is next

Pilot v0.1 proves that one player's evidence can deterministically unlock a mechanic. The next existential risk is multiplayer canonicality: two humans must be able to act in one world without duplication, contradictory ownership, or per-client truth.

## Recommended scope

Do not add Discord, LLM, NPC autonomy, news, or visual frontend yet. v0.2 should prove only this:

> Two players can inhabit one persistent world, race for the same resources, see each other's canonical actions, and produce independent behavior progression without corrupting state.

## Proposed acceptance criteria

- multiple player rows with stable external identity mapping;
- player creation is idempotent;
- two players can occupy the same location;
- inventory ownership is exclusive;
- simultaneous attempts to TAKE one item produce exactly one winner;
- ActionEvent stores each player's evidence independently;
- one player's progression cannot unlock another player's ability;
- transaction retry/busy handling is explicit;
- restart preserves all players and ownership;
- scripted two-player scenario passes repeatedly.

## Architecture options

### Option A — Extend current synchronous GameService

Add player lifecycle and concurrency tests around the existing SQLite transaction boundary.

Pros: smallest change, preserves proven core, easiest to reason about.
Cons: no transport layer yet.

### Option B — Introduce HTTP API now

Wrap GameService in FastAPI/ASGI while adding multiplayer.

Pros: directly prepares Activity/bot clients.
Cons: mixes two unknowns — multiplayer correctness and transport/auth — in one iteration.

### Option C — Build Discord adapter first

Use bot interactions as the first multiplayer transport.

Pros: immediate visible social prototype.
Cons: makes Discord bugs and game-state bugs indistinguishable; risks embedding domain logic in adapter code.

## Recommendation

**Option A.** Prove multiplayer canonicality in-process first. Then add a thin API/Discord adapter over a known-correct core.

## Explicitly deferred

- Discord Activity UI;
- bot channel mapping;
- LLM parsing/dialogue;
- autonomous NPC ticks;
- economy/businesses;
- morning newspaper;
- forgetting engine;
- monetization.

## Approval gate

This proposal intentionally stops before implementation. The next implementation cycle should begin only after the v0.2 design is approved, so transport/UI decisions cannot silently leak into the simulation core.
