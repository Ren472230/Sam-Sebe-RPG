# Правила автономной разработки

Этот репозиторий использует Autonomous Project Development v0.1.

## Источник истины

Перед любыми изменениями восстанови фактическое состояние проекта в таком порядке:

1. GitHub: текущие ветки, SHA, запросы на слияние, файлы и результаты проверок.
2. `RUN_STATE.json` после проверки записанных ссылок на фактический GitHub.
3. `CHAMPION_STATE.json` после проверки SHA и доказательств.
4. Утверждённые спецификации и планы проекта.
5. `docs/autonomy/ROADMAP.md`.
6. `AUTONOMOUS_LEARNING.md` и `docs/autonomy/DECISIONS.md`.
7. История текущего чата.

При конфликте фактический GitHub имеет приоритет. Подтверждённо устаревшие записи фиксируй во время сверки и исправляй после успешного захвата аренды.

## Жёсткий барьер аренды

**До успешной записи аренды запрещены любые изменения** кода, конфигурации, документации, веток и состояния проекта, кроме атомарной записи самой аренды в `RUN_STATE.json`.

**Сверка до захвата аренды выполняется только на чтение.** После атомарной записи аренды повторно прочитай `RUN_STATE.json` и убедись, что `active_run` содержит именно твой `run_id`, ожидаемую рабочую ветку и статус `running`. Только после этого разрешены остальные записи.

Если аренду захватил другой запуск, запись конфликтует или её успешность нельзя подтвердить, заверши запуск без других изменений.

## Перед началом работы

1. Прочитай `AUTONOMY_SYSTEM.json`.
2. Прочитай `docs/autonomy/PROJECT_CHARTER.md`.
3. Прочитай `docs/autonomy/RUNBOOK.md`.
4. Прочитай `RUN_STATE.json` и `CHAMPION_STATE.json`.
5. Только на чтение сверь авторитетную и рабочую ветки с GitHub.
6. Проверь действующую аренду запуска.
7. Захвати свободную или корректно восстановленную истёкшую аренду атомарным обновлением `RUN_STATE.json`.
8. Повторно прочитай состояние и подтверди владение арендой.
9. После этого выбери одну законченную единицу работы по правилам дорожной карты.

## Приоритет работы

1. Безопасность и сохранность данных.
2. Подтверждённые регрессии и красные обязательные проверки.
3. Блокеры активного этапа.
4. Следующая обязательная задача утверждённого плана.
5. Минимальная законченная часть текущего продуктового этапа.
6. Удобство использования и визуальная доводка после функциональной готовности.
7. Необязательные улучшения.

## Правила исполнения

- Продолжай существующий проект и его рабочие решения.
- Перед изменением изучи текущую реализацию и связанные проверки.
- При исправлении дефекта сначала получи воспроизводимое доказательство причины, если среда это позволяет.
- Избегай несвязанного рефакторинга.
- Используй рабочую ветку из `RUN_STATE.json`, если фактический GitHub подтверждает её актуальность.
- Сохраняй архитектурные инварианты из `PROJECT_CHARTER.md`.
- Один запуск должен оставить проект в понятном, проверяемом состоянии.
- Никогда не выдумывай результаты тестов, SHA, состояние веток, статус внешних действий или успешность записи.

## Проверка

После изменения запускай минимальные профильные проверки, затем обязательные связанные проверки проекта. Для утверждения готовности используй доказательства одного точного SHA рабочего результата.

Красная проверка становится блокером. Старый зелёный результат не считается доказательством для нового SHA.

## Семантика SHA передачи

`last_handoff.work_head_sha` хранит точный проверенный SHA рабочего результата до финального мета-коммита, который обновляет `RUN_STATE.json` и освобождает аренду.

Фактический текущий HEAD рабочей ветки после записи состояния всегда получай напрямую из GitHub. Не пытайся записать SHA коммита `RUN_STATE.json` внутрь самого `RUN_STATE.json`: такая самоссылка меняет SHA при каждой записи и не может быть атомарно точной.

## Действия владельца

Без отдельного явного разрешения владельца запрещены:

- слияние в `main`;
- публикация релиза;
- разрушительная миграция данных;
- удаление значимого пользовательского содержимого;
- изменение секретов, оплаты и внешних учётных записей;
- смена фундаментального технологического стека без доказанной необходимости;
- значительное изменение продуктовой цели;
- другие действия, которые `PROJECT_CHARTER.md` оставляет владельцу.

## Завершение запуска

Перед завершением обнови фактическое состояние и оставь передачу следующему запуску:

- цель цикла;
- что реально изменено;
- точный `work_head_sha`;
- выполненные проверки и результаты;
- подтверждённые блокеры;
- ровно одно `next_action`;
- необходимость решения владельца.

После успешной передачи атомарно освободи аренду в `RUN_STATE.json`, затем повторно прочитай файл и убедись, что `active_run.status` равен `idle`. После этого отдельно получи из GitHub фактический текущий HEAD рабочей ветки для отчёта владельцу.
