# Правила автономной разработки Sam-Sebe-RPG

Проект использует Autonomous Project Development v0.1 из `Persona-Ren/Autonomous-Project-Development`.

## Источник истины

Перед любыми изменениями восстанавливай состояние в таком порядке:

1. фактический GitHub: ветки, SHA, запросы на слияние, файлы и результаты проверок;
2. `RUN_STATE.json` после проверки записанных ссылок;
3. `CHAMPION_STATE.json` после проверки SHA и доказательств;
4. утверждённые спецификации и планы в `docs/superpowers/`;
5. `docs/autonomy/ROADMAP.md`;
6. `AUTONOMOUS_LEARNING.md` и `docs/autonomy/DECISIONS.md`;
7. история текущего чата.

При конфликте фактический GitHub имеет приоритет. Подтверждённо устаревшие записи обновляй в безопасной рабочей ветке.

## Перед работой

1. Прочитай `AUTONOMY_SYSTEM.json`.
2. Прочитай `docs/autonomy/PROJECT_CHARTER.md` и `docs/autonomy/RUNBOOK.md`.
3. Прочитай `RUN_STATE.json` и `CHAMPION_STATE.json`.
4. Проверь аренду активного запуска.
5. Сверь PR #53 и `integration/audit-results-v1` с фактическим GitHub.
6. Прочитай активный этап дорожной карты и связанный технический план.
7. Выбери одну законченную единицу работы.

## Приоритет

1. безопасность и сохранность данных;
2. подтверждённые регрессии и красные обязательные проверки;
3. блокеры активного этапа;
4. следующая обязательная задача утверждённого плана;
5. минимальная законченная часть текущего продуктового этапа;
6. удобство игрока и качество представления после функциональной готовности;
7. необязательные улучшения.

## Архитектурные правила

- Продолжай существующий проект и его рабочую архитектуру.
- Python/FastAPI и SQLite владеют каноническим состоянием мира и физическими последствиями действий.
- Языковая модель остаётся ограниченной диалогом и валидируемыми разговорными метаданными.
- Сохраняй детерминированность, причинную передачу знаний, персистентность и существующие границы Living World / Living NPC / Social World.
- Браузерные проверки пользовательского пути должны использовать реальное управление, если действующий план прямо требует этого.
- Избегай несвязанного рефакторинга.
- Никогда не выдумывай SHA, результаты тестов, состояние веток или успешность внешнего действия.

## Ветки

Авторитетная линия пилота: `integration/audit-results-v1`, PR #53.

Рабочая ветка установки и первых автономных циклов: `agent/autonomy-pilot-v0.1`.

`main` остаётся без изменений до отдельного явного разрешения владельца. PR #49 отдельно не сливать.

## Проверка

Для релизных утверждений используй результаты одного точного HEAD. Старые зелёные результаты другого SHA сохраняются как история и не доказывают текущую готовность.

Обязательный набор перед заявлением технической готовности текущего кандидата:

- Visual Forge Gate;
- Stream Slice Gate;
- Prototype Web CI;
- Playable Candidate Gate;
- Windows Compatibility Gate;
- Living World Integration Gate;
- Release Reproducibility Gate.

Реальная человеческая оценка игрового опыта остаётся отдельной контрольной точкой.

## Действия владельца

Отдельное явное разрешение требуется перед:

- слиянием в `main`;
- публикацией релиза;
- разрушительной миграцией данных;
- удалением значимого пользовательского содержимого;
- изменением секретов, оплаты и внешних учётных записей;
- сменой фундаментального стека;
- существенным расширением продуктовой цели.

## Завершение запуска

Перед завершением обнови фактическое состояние и оставь следующему запуску:

- цель цикла;
- реальные изменения;
- точный итоговый SHA;
- фактически выполненные проверки;
- подтверждённые блокеры;
- ровно одно `next_action`;
- необходимость решения владельца.

После успешной передачи освободи аренду в `RUN_STATE.json`.
