# Правила автономной разработки Sam-Sebe-RPG

Проект использует Autonomous Project Development v0.1 из `Persona-Ren/Autonomous-Project-Development`.

## Источник истины

Перед любыми изменениями восстанавливай состояние в таком порядке:

1. фактический GitHub: ветки, SHA, запросы на слияние, файлы и результаты проверок;
2. `RUN_STATE.json` после проверки записанных ссылок;
3. `CHAMPION_STATE.json` после проверки SHA и доказательств;
4. утверждённые спецификации и планы в `docs/superpowers/`;
5. `docs/autonomy/ROADMAP.md`;
6. `AUTONOMOUS_LEARNING.md` и `docs/autonomy/DECISIONS.md`;
7. история текущего чата.

При конфликте фактический GitHub имеет приоритет. Подтверждённо устаревшие записи фиксируй во время сверки и исправляй только после успешного захвата аренды.

## Жёсткий барьер аренды

**До успешной записи аренды запрещены любые изменения** кода, конфигурации, документации, веток и состояния проекта, кроме атомарной записи самой аренды в `RUN_STATE.json`.

**Сверка до захвата аренды выполняется только на чтение.** После атомарной записи аренды повторно прочитай `RUN_STATE.json` и убедись, что `active_run` содержит именно твой `run_id`, ожидаемую рабочую ветку и статус `running`. Только после этого разрешены остальные записи.

Если аренду захватил другой запуск, запись конфликтует или её успешность нельзя подтвердить, заверши запуск без других изменений.

## Перед работой

1. Прочитай `AUTONOMY_SYSTEM.json`.
2. Прочитай `docs/autonomy/PROJECT_CHARTER.md` и `docs/autonomy/RUNBOOK.md`.
3. Прочитай `RUN_STATE.json` и `CHAMPION_STATE.json`.
4. Только на чтение сверь PR #53, `integration/audit-results-v1` и рабочую ветку с фактическим GitHub.
5. Проверь действующую аренду запуска.
6. Захвати свободную или корректно восстановленную истёкшую аренду атомарным обновлением `RUN_STATE.json`.
7. Повторно прочитай состояние и подтверди владение арендой.
8. После этого прочитай активный этап дорожной карты и связанный технический план.
9. Выбери одну законченную единицу работы.

## Приоритет

1. безопасность и сохранность данных;
2. подтверждённые регрессии и красные обязательные проверки;
3. блокеры активного этапа;
4. следующая обязательная задача утверждённого плана;
5. минимальная законченная часть текущего продуктового этапа;
6. удобство игрока и качество представления после функциональной готовности;
7. необязательные улучшения.

## Архитектурные правила

- Продолжай существующий проект и его рабочую архитектуру.
- Python/FastAPI и SQLite владеют каноническим состоянием мира и физическими последствиями действий.
- Языковая модель остаётся ограниченной диалогом и валидируемыми разговорными метаданными.
- Сохраняй детерминированность, причинную передачу знаний, персистентность и существующие границы Living World / Living NPC / Social World.
- Браузерные проверки пользовательского пути должны использовать реальное управление, если действующий план прямо требует этого.
- Избегай несвязанного рефакторинга.
- Никогда не выдумывай SHA, результаты тестов, состояние веток или успешность внешнего действия.

## Проверка

Для релизных утверждений используй результаты одного точного SHA рабочего результата. Старые зелёные результаты другого SHA сохраняются как история и не доказывают текущую готовность.

Обязательный набор перед заявлением технической готовности текущего кандидата:

- Visual Forge Gate;
- Stream Slice Gate;
- Prototype Web CI;
- Playable Candidate Gate;
- Windows Compatibility Gate;
- Living World Integration Gate;
- Release Reproducibility Gate.

Реальная человеческая оценка игрового опыта остаётся отдельной контрольной точкой.

## Семантика SHA передачи

`last_handoff.work_head_sha` хранит точный проверенный SHA рабочего результата до финального мета-коммита, который обновляет `RUN_STATE.json` и освобождает аренду.

Фактический текущий HEAD рабочей ветки после записи состояния каждый новый запуск получает напрямую из GitHub. Не пытайся записать SHA коммита `RUN_STATE.json` внутрь самого `RUN_STATE.json`: такая самоссылка меняет SHA при каждой записи и не может быть атомарно точной.

Коммиты состояния после `work_head_sha` допустимы. При следующей сверке получи фактический текущий HEAD и проверь изменения после `work_head_sha`.

## Действия владельца

Отдельное явное разрешение требуется перед:

- слиянием в `main`;
- публикацией релиза;
- разрушительной миграцией данных;
- удалением значимого пользовательского содержимого;
- изменением секретов, оплаты и внешних учётных записей;
- сменой фундаментального стека;
- существенным расширением продуктовой цели.

## Завершение запуска

Перед завершением обнови фактическое состояние и оставь следующему запуску:

- цель цикла;
- реальные изменения;
- точный `work_head_sha` проверенного рабочего результата;
- фактически выполненные проверки;
- подтверждённые блокеры;
- ровно одно `next_action`;
- необходимость решения владельца.

После успешной передачи атомарно освободи аренду в `RUN_STATE.json`, затем повторно прочитай файл и убедись, что `active_run.status` равен `idle`. После этого отдельно получи из GitHub фактический текущий HEAD рабочей ветки для отчёта владельцу.
